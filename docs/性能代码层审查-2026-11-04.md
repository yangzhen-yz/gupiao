## 二、剩余可提升点（按收益排序，全部有实测数字）

### P0 · `/api/daily-reviews` 全量返回 518KB，而前端一页只显示 1 条 ★确定性大收益

**实测链**：

| 环节 | 数字 |
|---|---|
| 响应体 | `518235 B`，30 条 × 单条约 `24486 B`；单条最大字段 `tomorrowFocus` 9169B、`industrySectors` 4056B |
| 服务端 | `X-Process-Time: 133ms`（热态 166ms，是 53 端点里**唯一 >100ms** 的） |
| 传输 | gzip `105498 B`，走 cloudflared 隧道 |
| 浏览器 | `fetch 191.6ms`、`text 21.3ms`、`JSON.parse 2.6ms`（解析不是瓶颈） |
| 前端消费 | `TabReview.vue:607` `PAGE_SIZE = 1`，`totalPages = reviews.length / 1`；只有 `:895` 的汇总用 `slice(0, 3)` |
| 缓存 | 响应**无任何 `Cache-Control` / `ETag` / `Last-Modified`** → 每次开「每日收评」页都全量重查、重序列化、重传 |
| 数据源 | `load_daily_market_reviews()`：`SELECT * ... ORDER BY review_date DESC LIMIT 30` + 每行约 20 个 `json.loads`，在 `async def` 里**直接同步调用** |

也就是说：**为了渲染 1 天收评，付了 30 天的查库、序列化与传输成本，且每次开页都重付一遍。**

**修法（可叠加）**：
- **A · 零口径变更（推荐）**：进程内 SWR 缓存（收评一天才变，`ttl=300` / `stale_max=86400`）+ 同步查询包 `asyncio.to_thread` + 返回 `ETag`，`If-None-Match` 命中直接 304。首开仍 105KB，之后**服务端约 1ms、传输 0KB**。
- **B · 彻底减体积**：后端分页 `?page=&size=1` 返回当前页 + `total`，`518KB → 约 25KB`（**降 95%**），服务端约 5ms。代价：前端 `totalPages` 不能再由数组长度算，`slice(0,3)` 汇总需另给轻量接口或由缓存侧提供。
- **A+B 组合**最优：首次也只拉 1 页，翻页按需。

**预期**：热态最慢端点 166ms → 约 5ms；手机端重复开页省 105KB；顺带消除 P2 的偶发抖动。

### P0-A + P2：收评 SWR / ETag / 304 / to_thread

| 改动 | 文件 |
|---|---|
| `_DAILY_REVIEWS_CACHE`、`_build_daily_reviews_entry()`（预序列化 bytes + md5 ETag）、`_invalidate_daily_reviews_cache()` | `server/app/api/routes.py` |
| 路由改 `swr_get(...)` 在 `asyncio.to_thread` 里跑；`If-None-Match` 命中返回 `Response(status_code=304)`；正常响应用 `Response(content=raw)` 直出 | 同上 |
| 手动生成收评后写后失效 | 同上（收评 POST） |
| 定时任务生成收评后写后失效 + `_prewarm_misc` 增加收评预热 | `server/core/scheduler.py` |

**响应体结构、前端代码、分页口径一律未动**；新增头为 `ETag` / `Cache-Control: private, no-cache` / `X-Data-State`。
`private` 是为让带 `Authorization` 的响应仍可被浏览器私有缓存存储，`no-cache` 强制每次重验证 —— **只给 ETag 不给 `no-cache`，浏览器可能压根不存，条件请求就发不出来**。
304 对 `fetch` 是透明的（浏览器还原成缓存的 200 响应），`apiFetch` 无需改动。

自测 `scripts/daily_reviews_cache_selftest.py` **20/20**（进程内 ASGI，零外部请求）：首次 200 且结构不变、ETag 格式、304 空体、不匹配回 200、三次请求只构建一次、写后失效 ETag 变化、内容不变 ETag 稳定、通配符 `If-None-Match: *`、预压缩直出、Vary、gzip 可正常解码、identity 分支。

**首轮线上验收暴露的第二层（已补）**：缓存已命中（`X-Data-State: fresh`）时，无条件 200 的 `X-Process-Time` 仍是 **96ms**，而 304 只有 3ms —— SWR 省掉了查库 + JSON 编码，但 **GZipMiddleware 每个请求把 518KB 重压一遍**。故把 `gzip.compress(raw, compresslevel=6)` 也缓存，响应自带 `Content-Encoding: gzip`（中间件见已有该头直接放行，自测确认无双重压缩）与 `Vary: Accept-Encoding`；不收 gzip 的客户端返回 identity 原文。补完无条件 200 的 XPT **1～4ms**、total 10～30ms（本地直连传 105KB），304 为 0B；等预热链静默 30s 后复测 8 次，XPT 稳定在 **2～4ms**（首请求 39ms 为冷连接）、total 13～35ms，304 `7.6ms / 0B / XPT 3ms`，identity 分支 `48ms / XPT 2ms`。完整链路 `133ms → 96ms → 2～4ms`。压缩级别 6 比中间件默认体积大 2.7KB（108172B vs 105498B），换每请求省 90ms+。

**浏览器验证的判定坑**：Playwright 应用层看到 200 是 Chrome 把 304 透明还原成缓存的 200（还带着缓存的 `content-length: 105498`），不能据此判失败。CDP 网络层 `responseReceivedExtraInfo.statusCode` 才坐实：首次 **200 / encodedDataLength 105791B**，重复开页 **304 / 200B**；页面文本 4203 字、零 JS 异常。

### P1：由「按单票缓存」改判为「根治 N+1 权重查询」

**为什么不按原计划做**：读代码发现扫描是「整池一次性拉行情 + 逐票评分 + 全池行业中性化」，按单票拆要重构约 300 行；且 `apply_industry_neutralization` 会**原地修改** `stock['score']`，复用缓存必须深拷贝；权重与口径开关经 `app_settings` 热改后不在评分输入里，缓存有返回过期分数的风险。为 0.8s 引入这些风险不划算。

**实测定位**：阶段日志 `候选+范围 0.03s / 行情 0.26s / 附加数据 0.14s / 评分+趋势缓存 0.78s / 落库 0.07s`；进程内逐项量到 `calc_stock_score_v2(stock)` 不传 `weights` 时，函数内部 `if weights is None: weights = load_strategy_factor_weights()` —— **每票查一次权重表，14.31ms/次 × 59 只 ≈ 844ms**。这是典型 N+1，与缓存键粒度无关。

**修法**：`routes.py` 批量扫描、`services/pick/recommend.py` 智能推荐两处循环，改为循环外 `await asyncio.to_thread(load_strategy_factor_weights)` 查一次并显式 `weights=` 传入；异常时退回 `None`（等价旧行为）。`services/strategy/trend.py` 本来就在循环外查一次并传入，无需改。自测 `scripts/scan_weights_nplus1_selftest.py` **8/8**，含「不传 weights 确实查表」的反证与「两种调用评分结果逐字段一致」；真实 DB 下 60 次评分 **871.2ms → 2.8ms（307×）**。

### 7.3 P3：并发压测反证，判定「不改架构」

先纠正一个事实：`core/scheduler.py` 在独立线程里跑，每个任务各自 `asyncio.run(...)` 建**临时 loop**，`to_thread` 用临时 loop 自己的 executor —— **定时任务本来就不共享 uvicorn 主 loop 的 48 线程池**；预热项也是独立 `threading.Thread`。真正共享主池的长任务只有 API 触发的趋势后台重扫 `trend._start_bg_rescan()`（`asyncio.create_task` 挂在主 loop）。而 `_get_scan_lock()` / `get_scan_semaphore()` 是**按 loop 重建** `asyncio.Lock`/`Semaphore`（防「锁不跨 loop」），把重扫协程搬去独立 loop 会让主 loop 与后台各持一把锁、单飞闸门失效 ⇒ **风险大于收益**。

因此本轮不改调度架构，改做 §五待办要求的**并发压测反证**：借重启后预热链活跃窗口，200 秒内每秒并发采样 `health` / `daily-reviews?page=1` / `?page=2` / `market-index`，共 **764 条**（报告 `server/analysis_out/p3_concurrency_probe.json`）。

| 端点 | 预热期(0～70s) wall p50/p95/max | 预热期 XPT p50/p95/max | 静默期(130～200s) wall p50/p95/max | 静默期 XPT p50/p95/max |
|---|---|---|---|---|
| health | 2.9 / 21.2 / **2027.5** ms | 1 / 5 / 287 | 2.2 / 4.7 / 6.6 ms | 0 / 1 / 3 |
| reviews?page=1 | 3.3 / 16.5 / 123.0 ms | 1 / 6 / 100 | 2.8 / 4.4 / 8.4 ms | 1 / 2 / 4 |
| reviews?page=2 | 3.1 / 28.7 / 140.0 ms | 1 / 5 / 137 | 2.7 / 5.1 / 7.2 ms | 1 / 2 / 4 |
| market-index | 3.0 / 53.6 / 360.8 ms | 1 / 39 / 359 | 2.3 / 4.2 / 7.3 ms | 1 / 2 / 2 |

**结论**：`XPT > 100ms` 仅 **5/764（0.65%）**，全部集中在预热链活跃的 0～83 秒；静默期全部接口 p95 ≤ 5.1ms、XPT ≤ 4ms。最扎眼的是 44～53 秒 `health` 三次 1.2～2.0 秒长尾，其中一次 `XPT 仅 1ms` 而 wall 1603ms ⇒ 请求在到达服务前排队（GIL / accept 层），不是接口计算慢。**这是偶发长尾，不是系统性饱和**，与 §三「实测否定：别为未复现的瓶颈改调度架构」一致。专用线程池的收益面就是这 0.65%，代价是跨 loop 闸门重构，本轮不做。

**若将来要做，前置条件**：先把 `_get_scan_lock` 的单飞闸门换成进程级 `threading` 闸门（保证跨 loop 互斥），再谈专用 executor；只换池子会让并发扫描失控。
