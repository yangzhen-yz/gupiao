### 8.3 样板：复盘缓存是怎么治好的（三条可复用的判据）

实现细节归 README 技术说明与 `docs/工程知识库.md`（白名单 `(30,120)`、上限 8、按 `used` 淘汰、burst 之后仍命中 0.007s / 0.061s、自测 24/24），这里不重复。留给后面几条抄的只有三条判据：①键要先归成前端真会发的枚举；②淘汰按"最久没被访问"，不是整表 clear；③验收判据要从"命中快不快"换成"一串垃圾参数之后还命中吗"。

### 8.4 趋势扫描"首开冷扫"：盘中其实不存在，冷的只有三个窗口

证据链：

1. 调度器交易日 09:00~15:00 每 30 分钟扫一次（`scheduler.py:1010` 生成 13 个时点，`job_scan_trend` 有 `_today_is_trading()` 守卫）。
2. 调度器跑在**同进程**的守护线程里（`app/main.py:273`），而 `_last_scan_result` / `_last_scan_date` / `_last_scan_ts` 是 `trend.py` 的模块全局——调度器扫完，主 loop 上的请求就命中内存，**所以盘中首开不冷**。
3. 库里能对上：`trend_scan_results` 每行有 `created_at DATETIME DEFAULT (datetime('now','+8 hours'))`，且写入是 DELETE-then-INSERT，所以它是**当天最近一轮扫描的精确时刻**（实测 11-02 15:01:49、10-30 15:00:14＝15:00 定时档；11-03 23:59:09、11-04 07:56:53＝我手动点的那两次）。
4. 真正会冷的窗口只有：09:00 之前、15:00 之后（含我们每天盘后重启）、周末与非交易日。我这两天撞到的 16.4s / 18.1s 全在这里。 **但这条在 11-04 上午并不成立**：当天定时扫描因为 SWR 挂在调度器临时 loop 上被取消、根本没落库，数据冻结在 09:00:31（另一路已修，见 §6）。"设计上有 13 轮"不等于"实际在刷"——以后判这类问题要同时看库里 `created_at` 和日志，别只读调度表。修复后本条结论才成立。
5. 成本结构：07:56 那轮日志显示扫描池只有 57 只（"股票范围…94 → 57 只"）、"批量行情预取 57/57 可复用"，仍耗时 16.4s——**慢在逐票取数，不在线性于池子大小**，所以"缩小扫描范围"这条不是解药（未做对照实验，此判断为推断，需实测才作数）。

### 8.5 三个选项与推荐

| 选项 | 做法 | 收益 | 代价与前置 | 结论 |
|---|---|---|---|---|
| A 启动预热 | 起一条线程跑一次扫描（现成范式见 §8.8 一/二），但**前置是先补跨 loop 单飞**（§8.8 三） | 首开即热 | 每次重启花 16~18 秒外部取数+写库，而重启几乎都发生在盘后/夜里＝收益落在没人的时段 | 前置已知、可做，但不如 B 划算 |
| B 启动读上次落库结果 | 内存为空时用 `load_trend_scan_results()` 填 `_last_scan_result`（`_last_scan_ts=0` 自然走陈旧那一支），`load` 多返回一个 `scannedAt=created_at`，UI 非当天时把"数据扫描于"补成带日期 | 晚间首开从白等 16 秒 → 立刻看到上一轮名单＋明确日期＋后台自动重扫＋前端按 [8,15,25,35,65] 秒退避再取 | 一次 SELECT，零外部请求；`TabTrend.vue:10` 已能吃空 `scanAt`（显示"扫描时刻未知"），改动很小 | **推荐** |
| C 只改文案 | 首开给个进度提示 | 体感 | 白等仍在 | 弱，不单独做 |

选 B 就必须一起接受一个语义变化：**09:00 前后打开页面的人会先看到昨天的名单**（带"11-03 15:01 扫描"标注）。如果你认为"宁等 16 秒也不要看到昨天的票"，结论就该反过来——只做 A（并先补跨 loop 单飞），不做 B。**这一条要用户拍板，是本备忘唯一的待决项。**

A 的前置条件（无论选不选 A 都该知道）：`trend.py::_get_scan_lock()` / `get_scan_semaphore()` 带 `_bound_loop` 判据，当前 loop 与创建时不同就**重建实例**（探针：两次 `asyncio.run` 取到的锁与信号量 `is` 比较均为 `False`）。含义是互斥只在同一个 loop 内有效，因此 9:00~15:00 的定时扫描与主 loop 上的请求扫描**不互斥**，理论上能同时跑两轮全市场扫描、并发额度各一份（`SCAN_CONCURRENCY` 翻倍打到腾讯）。这是既成事实，不是 11-03 的 SWR 带入的。

### 8.7 优先级与最小改法（前三名，各自独立可交付）

1. **`_HOT_SCAN_CACHE`**（`routes.py:40`，路由无鉴权）：无上限无回收 + 单值全站最大 + 键是可选池排列组合。最小改法：键换成稳定短键（自选池内容 hash，而不是 120 串代码拼接），加 `_HOT_SCAN_MAX_KEYS` + 按 `used` 淘汰——**直接复用已经写好的 `_remember_rec_review`/`_touch_rec_review` 那一对**（`routes.py:743-762`），再给 `codes` 加"必须属于本会话可见池"的成员校验。
2. **`_EXCESS_CACHE` + `_REC_SIM_CACHE`**（三个公开路由）：参数先归档成枚举再进键（`months∈{3,6,12}`、`capital` 落档位、`gap` clamp 到固定步进，白名单外只现算不入表），三处 `clear()` 换成逐条 LRU，`('batch', ...)` 与 `(months,)` 拆成两张表互不牵连。`excess` 先做，因为一次清空＝7.4 秒。
3. **`_realtime_cache`**（`stock.py:14`）：键标准化成 `','.join(sorted(set(合法码)))`，写入时顺手 pop 掉 `age>60s` 的条目 + 条数上限 LRU，替掉"只判龄不回收"。它被全站复用，改这一条的收益覆盖面最大，但它是**最底层**的缓存，改动要配并发与命中的自测再上。

并列关注（统一治理时一起改，不单独立项）：`fundflow._CACHE` 零淘汰（+删死代码 `_hidden_key`）、`rps._LB_CACHE` 的 `top_n` 夹紧、`action_desk._DESK_CACHE` 的 `phase` 做枚举校验；**`_ONDEMAND_TREND_CACHE` 的日级失效已于 11-04 晚单独收口**（按日失效 + 5 分钟 TTL + 逐条淘汰），此项从待办划掉。

**统一治理的正确形态**：与其在 9 个地方各写一遍淘汰，不如把这 9 个 caller-keyed 缓存收敛到一个几十行的辅助件（`get/set(whitelist, max_keys, ttl, key_of)`，淘汰按 `used`），核弹 clear 一次性退役。这是**架构级改动，要单独立项**，不顺手做。

### 8.8 跨 loop 单飞：本仓已有三种现成范式，趋势扫描该抄第三种

| 范式 | 位置 | 形态 | 适配趋势扫描？ |
|---|---|---|---|
| 一 | `routes.py:652-696` | `threading.Lock` + 全局 bool + 子线程 `asyncio.run` + `generation` 防旧结果回写 | 能做预热，但要自己管 loop 与结果覆盖顺序 |
| 二 | `routes.py:49-77`（复制版 `market.py:173-190`） | `threading.local()` + 按 key 节流 dict，子线程内标记 `compute=True` 防自递归 | 适合"同一 key 20 秒内只刷一次" |
| 三 | `sentiment.py:51, 725-750`（复制版 `mainline.py:577, 598-604`） | **事件循环内非阻塞抢 `threading.Lock`，抢不到就直接返回旧值，绝不同步等待** | **最合适**：注释里已经写明"在 async 里阻塞等锁会冻住整个事件循环，实测白堵 2 秒"，与趋势扫描"拿不到锁就回旧数据 + stale"的语义完全一致 |

趋势扫描现状的准确描述：`_swr_refresh_inflight` 是裸 bool（`trend.py:76`），但在**同一个 loop 内没有竞态**——`_start_bg_rescan()`（`:164-169`）是先同步置 `True` 再 `create_task`，协程式调度不会在两句之间切走。真正的缺口是跨 loop：调度器 9:00~15:00 的扫描跑在自己的 loop 上，**既不查这个 bool、也不共用那把锁**（锁带 `_bound_loop` 判据，换 loop 就重建），所以预热/定时扫/用户请求三者之间没有互斥。要补的就是把 bool 那一步换成范式三的 `threading.Lock` 非阻塞抢占。
