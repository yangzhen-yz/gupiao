## 1. 部署与工程

- **端口是 3003**（不是 8000）。启动器 `server/analysis_out/serve_3003.py`（uvicorn run:app reload=False，与隧道守护同口径）；`run.py` 的 reload=True **不能当热重载用**——2026-10-23 实测：日志打印 `StatReload detected changes ... Reloading...`，但旧 worker 没退、新 worker 没起，请求仍由旧代码回答（新接口 404/500），端口还挂在已死的 reloader PID 上。**假重载识别法**：出现 "Reloading" 后必须看到新的 `Started server process [PID]` + `Application startup complete`；否则按未重载处理。重启 = 先 `Stop-Process` 杀 reloader、再查并杀遗留 worker（`Get-NetTCPConnection -LocalPort 3003` 找真正持有者），`netstat` 确认 port-free 再起；守护（`tunnel_watch.py`，按端口+HTTP 检测、不按进程名，不会误杀）30 分钟冷却内可自起重启
- **Python 解释器**：`.venv` 存在（`gupiao/.venv/Scripts/python.exe`），但**里面没有 numpy**（系统 Python312 有）；2026-10-23 起服务改用**系统 Python312 直接跑 `serve_3003.py`**（无 reload、单进程），新依赖仍要两边都验。**即便系统 Python312 独立能 import numpy，reload worker 里仍可能没有**（2026-10-23 因子体检踩过：`/api/eval-lab/latest` 500）——判断依赖要看"服务进程"而不是终端里的 python；pandas/numpy 这类离线分析不要塞进 web 进程，走子进程。系统 Python312（`C:\Users\Administrator\AppData\Local\Programs\Python\Python312\python.exe`）依赖齐全，自测/离线脚本仍可用它；沙箱 Bash 里 `python` 指向 workbuddy 托管 3.13，缺依赖，别用
- **改完代码怎么让后端换新版（2026-10-23 晚踩坑后定的正路）**：看护计划任务以 **SYSTEM** 拉起后端，工具会话（非管理员）`taskkill` 它报"拒绝访问"，自己再 `Start-Process` 起一个会因为 3003 被占直接 `[Errno 10048]` 退出——而它在 lifespan 里已经把热搜榜拉了一遍并打印"Application startup complete"，日志看着像重启成功，实际还在答旧代码（当晚接口迟迟不返回新加的 `source` 字段就是这个原因）。正解：写标志文件 `server/data/backend_restart_requested`，看护下一轮（≤5 分钟）读到即杀进程树→等端口释放→拉起→删标志→推企微；工作日 09:10~15:10 之间只推迟不重启，避免打断 09:45/14:45 批次。21:41 写标志、21:46 完成重启（PID 23436→29492）。**判据别看 health 200，要看"接口里新字段有没有"**。（补充：`Start-Process` 本机今天实测可用，能起进程、只是抢不到端口；上一条"被安全策略拦截"的说法已过时）
- **`_reload_config()` 会制造"旧函数体 + 新全局表"（2026-10-29 事故，已修）**：`app/main.py` 检测到 `config.py` mtime 变化会 `importlib.reload` `services.data.stock` / `services.strategy.trend` / `services.pick.recommend`，但别的模块启动时 `from ... import 函数` 拿到的仍是旧函数对象——旧函数体的 `__globals__` 已指向重载后的模块。一旦内部 helper 的签名跨版本变了，就会报 `_build_expectation_note() takes 3 positional arguments but 4 were given`：批量扫描与 `/api/stock/{sym}/full` 全线 500，而 `/api/health` 一直 200。**修法（2026-10-29 19:30 补齐根因）**：① `app/main.py::_reload_config()` 不再 `importlib.reload` 任何业务模块，只重载 `app.config`——全仓 33 处顶层 `from ... import` 因此不会再有"旧函数体 + 新全局表"的混用；② `routes.py` 统一写成 `from services.pick import recommend as _recommend_svc`，买卖点与 `auto_generate_recommendations_task` 都走 `_recommend_svc.xxx`，将来即使恢复 reload 也不再踩；③ 代价：直接改 `config.py` 的常量需重启后端（写 `server/data/backend_restart_requested`），常改开关走 `app_settings` 覆盖表（每次取值现读，不受影响）。本次 07:33 写重启标志、07:37 完成重启（PID 5620→6880）；19:31 写标志、19:41 完成重启（PID 12112→464）后 touch `config.py` 实测只打印"app.config 已重载"、无"已重载 services.…"。判据用接口字段：`/api/tab-scan-config` 不再下发 `leadersMinGain`、full 接口不再报错且有 `sellPct` 无 `stockType`。
- **测本机接口必须 `curl --noproxy '*'`**：环境代理会拦截 127.0.0.1，后端真挂了返回假 502，真连不上才是 000
- **连库必须绝对路径**：曾在仓库根(cwd)误建 0 字节空库；Windows Python 打不开 `/d/...` 风格路径，用 `D:/Desktop/...` + `?mode=ro` URI
- 前端 `client-vue/` Vue3 **无 dev server**，改完必须 `vite build`，产物托管在 `server/static/`
- **提交/推送的硬拦截在 `.githooks/`，不在文档里**（2026-10-23 上线）：`AGENTS.md`/`CONTRIBUTING.md` 只是指令，写"禁止 `git add .`"拦不住一次真实的 `git add .`（本仓常年几十个未跟踪文件 + 构建产物删增对）。启用是一次 `git config --local core.hooksPath .githooks`，停用 `--unset` 即回到改造前；pre-commit 四项阻断（落后于 origin / 疑似批量 add / 产物删增不成对 / 新增行含本机绝对路径或 webhook 字段）+ 一项只提醒（改了代码没带文档），pre-push 拦非快进推送。零第三方依赖（Git 自带 sh，不用 pre-commit 框架、没装 gh）。**GitHub 分支保护仍待用户在网页开**（本机没 gh，且实测此刻 `github.com:443` 连不通），所以"B1 落后拦截"目前只在能连上 origin 时才生效，现在走的是 fail-open 警告分支。**分支流程的本仓特有约束：服务只在 `main` 上跑**——`:3003` 由仓库外计划任务按固定路径拉起，切分支就是换线上代码，因此盘中 09:10~15:10 禁止 `git switch`/`merge`/`rebase`；改动合入 main 后靠 `server/data/backend_restart_requested` 标志让看护重启生效。**切回 main 前必须先 fetch 成功**：本机到 `github.com:443` 间歇不通（实测 `api.github.com`=200 而 `git ls-remote origin` 全失败），此时本地 `refs/remotes/origin/main` 是合并前的旧值，直接 `git switch main` 会把工作树换成旧代码、线上立刻降级——判据是 `git log --oneline -3 origin/main` 能看到预期的合并提交
- **hook/脚本的提示文案里不要写反引号包裹的命令**（2026-10-23 验收时自踩）：pre-commit 的失败信息里写了 `` `git add .` ``，双引号内被 shell 当命令替换执行，**hook 自己把整个工作树 add 了**（暂存数 0→84）。恢复只需 `git reset`（mixed 不动工作树内容）；文案改成单引号形式后复验"跑完 hook 暂存数不变"。同类风险：提示串里的 `$(...)`、反引号都会被求值
- Git Bash 里 `taskkill /PID xxx` 会被 MSYS 路径转义破坏 → 用 PowerShell `Stop-Process -Id xxx -Force`
- 数据库：`server/gupiao.db`（主库，含 `auction_snapshot` / `limit_pool_daily` / `eval_lab_runs` 等新表）+ `server/data/history_kline.db`（本地历史K线/RPS/市值表）+ `server/data/history_minute.db`（5 分钟线 `minute_5m`，前向采集默认关；路径写死在 `services/data/minute_history.py`，不在 `app/config.py`）

## 2. 数据源坑

### 东方财富
- **三套行业分类互不互通（2026-10-22 主线功能实锤）**：涨停池 `hybk` 与板块榜 `f14` 是**东财行业名**（通用设备/照明设备/IT服务Ⅱ）；`stock_industry_map` 与新浪聚合板块是**baostock 国标名**（C39计算机、通信和其他电子设备制造业）。跨分类 join 会静默 0 行——主线用 `sector_taxonomy_vote`（代表股逐日投票，≥3 票且 share≥60% 才认映射），未成熟宁可"持续性缺维＋dataGaps 点名"也不瞎配。另外**收评 `industry_json` 只存当日涨幅前 20 行**，没上榜的板块当天无记录——绝不能当板块持续性历史（缺失会被误读成不涨），持续性必须走本地日K聚合
- **调度器里等不了"后台起算、本轮返回 None"的设计（2026-10-22）**：`_sina_market_snapshot` 为页面轮询设计——最多等 6s、扫描丢后台继续。调度器预热用的是 `asyncio.run` 的**一次性事件循环**，run 返回即关循环，后台扫描被杀 → 保活永远拿不到结果还不自知；**更毒的是 `_SINA_COMPUTING` 标志因 finally 没机会执行而卡 True，之后所有保活直接 return False，主线整天"无资金"**（11:06~11:12 实拍，重启才清）。凡在调度器线程里依赖异步缓存填充的，必须直接 `await` 算完（新浪全市场 ~15s，调度器是独立线程，代价是本轮 tick 晚 18s，30 分钟一次可接受）

### 情绪备源与"封板"判定（2026-10-28）
- **东财不是唯一源，但只有它给现成池子名单**：涨停/跌停家数与涨跌家数都能用「新浪排行 `changeratio` 分页 + 腾讯批量昨收」重算（10-27/10-28 东财封禁那两天，腾讯 `quote` 1823/1823、新浪 `quote` 7266/7276 全成功）；连板梯队与昨日涨停溢价本地日K就能算。百度/同花顺排行/广发都不可批量，不在这条链的候选里。
- **封板必须比"现价 == 理论涨跌停价"，不能用涨跌幅容差**：低价股四舍五入到分之后，真实跌停的涨跌幅可以是 −9.91%（昨收 5.55 → 跌停 5.00），而 −9.98% 未必封住（主板 −9.98% 是"砸到附近没封"）。用 `≥9.95%` 这类容差判，今天跌停会从 7 只误算成 12 只。
- **涨停价要用 `Decimal(...).quantize(0.01, ROUND_HALF_UP)`**：Python 内置 `round` 是"四舍六入五成双"（`round(6.175, 2) = 6.17`，交易所给 6.18），低价股差一分就漏判，实测少算 2～3 只涨停。
- **昨收不能靠涨跌幅反推**：反推得到的昨收带比率误差，在低价股上会跨越那一分；要拿准昨收就用腾讯批量 `fields[4]`（或本地日K，但注意日K同步只覆盖约 2458 只、且有滞后与除权日问题）。
- **请求量与频率**：涨跌家数要扫全市场（实测 6000 行 / 60 页 / 约 35 秒），**不能进 180 秒快循环**，单独 5 分钟 TTL；涨停/跌停只扫两端各 8/6 页 + 对候选（今天 93 只）补昨收，实测 8.5 秒，每轮跑得动。
- **`strategy_snapshot_batch.gate_min_score` 存的是 advisory（影子）口径**，不是 live 生效值（`strategy_snapshot.py` 取 `gate['advisoryMinScore']`）；live 门槛看 `min_score` 列。10-28 就因为它把"退潮日门槛被抬到 68"说成了事实，实际 live 一直是 60 —— 读列名推断口径是本表最容易犯的错。
- **家数统计一律剔除 ST/*ST（2026-10-28 用户口径，优先于"对齐东财"）**：涨停、跌停、涨跌家数、候选池统一走 `sentiment_alt.is_st()`（转发 `universe.is_st_name`，按"名称含 ST"判，天然覆盖 ST/*ST/S*ST/SST 等变体，并把名称带"退"的退市整理一并剔除），不进分子也不进分母。返回体带 `excludeSt: True` 与 `stExcluded{zt,dt,breadth,names}`；`limitUpInclSt`/`limitDownInclSt`/`totalInclSt` 只为"剔除前/后"对照而留，**接情绪值时只许读剔 ST 后的字段**。今日（10-28 收盘）实测：涨停 **72 → 70**、跌停 **8 → 7**，ST 占涨停 2 只（`*ST萃华`（行情源显示"萃华退"）、`*ST和科`）、跌停 1 只（`*ST建艺`）。
- **ST 没有 5% 档，第一版按教科书写错了**：`_limit_ratio` 原来给 ST 开 5%，被今天的数据推翻——`*ST和科` 17.94 对昨收 16.31 正好 ×1.10 且封在买一；主板 259 只 ST 近 3 个月有 **137 只**出现过单日 |涨跌| > 5%（最高 10.71%），若是 5% 板这些记录不可能存在。ST 实际与主板同档 10%；按 5% 判会把 `*ST和科` 这只真涨停漏掉（对照数变成 71 而非 72）。因为 ST 整体剔除，这个修正只影响"剔除前"的对照数。
- **涨跌家数的分母只数沪深京 A 股**：新浪排行 6000 行里混着 ETF（sh51/56/58，实测 314 行）与 B 股（900/200，97 行），它们不是股票、不该算"家数"。收口后 A 股 5588 只，再剔除 ST/退 393 只 → **5195 只（涨 4109 / 跌 862 / 平 224）**；旧口径把 6000 行全算，是 4455/1013/532。
- **东财只作参考、不再对齐**：东财自己同一天就会变——15:05 收评快照 73/6（`daily_market_reviews`），20:1x 再调池接口是 72/5。逐票差可解释——东财多 3 只（`萃华退` 是 ST；`920220`/`920896` 是北交所新股，我们按"新股不参与"剔除），我们多 1 只涨停（`605488 福莱新材` 48.61 = 44.19×1.10，尾盘封板）与 2 只跌停（`002488 金固股份` 6.17=6.86×0.90、`603696 安记食品` 14.31=15.90×0.90，收盘都封在理论跌停价），东财池未收录。**家数不一致时先比名单、再用"现价 == 理论涨跌停价"裁决**，别用百分比容差去猜。

  v2 放宽买入可行性后若继续共用，就会把「封板票走次日竞价买」这条分支一起取消（实测 auction
  剔除从 23 掉到 6、收益 +24.8 个点——那不是更真实，是涨停票改按当天涨停价买，反而更乐观）。
  正确拆法：`sealed_at_close`（收盘钉在涨停价 → 走次日竞价）与 `sealed_hard`（全天没低下去过 → 才可剔除）。
  另外**走完竞价买入分支后两个标记都要清空**，只清一个会被下一道剔除再杀一遍（这个 bug 是自测抓的）。
- **卖出的可成交性判据旧实现漏了半个**：跌停顺延只写在 `mode=='open'` 里，`close`（尾盘卖）连检查都没有，
  等于假设一字跌停还能按收盘价出——**凡是"卖不掉"这类约束，两种卖法都要判**，否则回撤系统性低估。
- 涨停/跌停价必须按 `round(前收×(1±板幅), 2)` 算，别用"涨幅≥97%限额"近似：低价票四舍五入后会判错，
  而"封没封死"恰恰差一分就判反。
- 放宽可行性得到的新数字要当场标成"上界"：尾盘入口纳入 57 笔炸板回封票后从 -41.74% 变 -9.43%，
  唯一乐观之处是假设排队必成——日线证明不了尾盘那一刻的封单强度，所以旧口径（全剔）留着当下界，
  两个开关都关就等于它。

- **覆盖表 `value()` 返回的是"界面单位"，不是 config 单位**：SPEC 里 `scale=100` 会把 config 的 `0.015`
  变成界面上的 `1.5`。所以凡是从 `app_settings.value()` / `_setting()` 取来的数值，先确认它的单位再进公式。
  仓位规则这次的正确处理是：`risk÷stop` 两个都是百分数、相除无量纲，直接就是仓位比例；而 `cap`、`exposure`
  必须再除以 100 才回到比例。写错的后果是 100 倍仓位（或 1/100），`position_sizing_selftest.py` 第 4 节专门钉这条。

## 4. 系统架构要点

### 多用户账号体系（2026-10-12）
- **只隔离私有数据，不做全站登录门禁**：持仓私有（`/api/positions*` 强制鉴权）；行情/推荐/收评/趋势公共免登录——收评定时任务、推荐快照、截图脚本等既有自动化零影响
- `user_positions` = user_id 列 + `UNIQUE(user_id,symbol)`（原 `UNIQUE(symbol)` 会让多用户持同票冲突，SQLite 不能 ALTER 唯一约束只能整表重建）
- ⚠️ **用户 id 必须显式 `MAX(id)+1`**，不能用 AUTOINCREMENT：存量持仓归 user_id=1，依赖自增会让 sqlite_sequence 前进后首个注册用户拿不到 1
- 认证 PBKDF2-SHA256 + secrets 盐；会话 token_urlsafe(32) 存库（免 JWT）；失败 5 次锁 5 分钟；`current_user` 认 Bearer 或 X-Auth-Token；首个注册账号自动认领存量持仓
- 前端 `apiFetch` 自动带 token、401 清登录态；`TabPosition` 经 `defineExpose({loadPositions})` 换账号即时重载

### 性能架构（2026-10-17 专项）
- **threading.Lock 在 async 上下文 `acquire(timeout=N)` 会冻住整个事件循环**（同步等锁，定时器都无法触发）→ 必须 `acquire(blocking=False)` 快速失败
- **`asyncio.wait_for` 对 `to_thread` 任务超时不取消线程**（要等线程结束才交付）；"超时即释放 singleflight"是错的
- 情绪非交易时段（2026-10-23 晚改）：**收盘定版不走 TTL/singleflight**，`get_sentiment()` 直接 `_final_fallback()` = 今日收评 → 今日最近 `stale=0` 盘中快照 → 最近收评。`final=True` 只决定前端措辞"收盘定版"，`stale=True` 仍保证不给否决权（两者必须分离：定版不是数据坏了，但也绝不在收盘后重新开启盘中拦截）。周末/节假日 `final` 日期为最近交易日，卡片写"休市 · 参考 MM-DD 收盘"。**盘中实时不可用时的兜底链**：进程缓存 → 当日最近一次 `stale=0` 盘中快照（≤`SENTIMENT_SNAPSHOT_FALLBACK_MAX_AGE_SEC=21600` 秒，覆盖 09:15～15:05 整个交易时段、仍限当日）→ 最近收评；快照兜底 `source=snapshot_fallback`、保留原 `asOf`，`dataGaps` 写"沿用 HH:MM 盘中快照（已 N 分钟未更新）"；2026-10-28 角色体系删除后不再写 `rule.veto_roles`（旧快照里的同名字段已无人读取）。`_maybe_save()` 拒绝写 `stale` 数据，避免 `INSERT OR REPLACE` 覆盖同 `ts` 的 live 行
- **并发教训（2026-10-23）**：行动台同时发起 `get_sentiment()` 与 `get_mainline()`；非交易时段前者抢 singleflight 失败会返回没有 `final` 的"刷新中"空壳，后者据此把今日结构判成"不可用"并缓存 180 秒。现在非交易时段绕过锁直接读本地收评；mainline 抢锁失败先 `peek_cached()` 最近真值，仍为空则**不写缓存**，下一轮重新尝试
- 分层缓存：action_desk 交易时段 8s/休市 60s；universe.selectable 10 分钟 + scheduler 启动预热；daily_recommendations 整档 30s（写后置失效）；腾讯批量按整串 key 缓存
- 终值（周六 closed）：action-desk 冷1.65s/温0.024s、settings 0.50s、market-index 0.076s、stock/full 0.82s、daily_recs 0.66s、fund-flow 2.07s、ai-diagnose 17.8s
- **to_thread 默认线程池被扫描打满（2026-10-24 修复）**：asyncio 默认执行器 = `min(32, CPU+4)`（本机 12 核 = 16 线程），趋势扫描并发 25、每票至少占 2 次 to_thread（本地日K + 单码行情），扫描期间全局线程池被打满、全站 to_thread 排队——10-24 上午实测连鉴权 401 拒绝都要 27.8s 才返回（同期 fund-flow 冷 9.76s）。修复：lifespan 里 `set_default_executor(ThreadPoolExecutor(max_workers=config.TO_THREAD_POOL_MAX_WORKERS=48))`（扫描是 IO 密集，放大线程数不挤 CPU）。同批三件：① **趋势扫描行情复用**——板块动量预计算此前已把全池 100 只/批拉过一遍、只用涨跌幅就丢弃，`process_one_stock` 又逐只单拉 ~1300 次单码腾讯请求（`_realtime_cache` 按整串 key 缓存、单码 key 命不中，且 TTL 仅 5s 也等不到）；现 `stock.split_batch_raw()` 拆串后经 `_load_kline_for_scan(symbol, realtime_raw_prefetched)` 直传复用，外部请求 ~1300 次 → ~13 次批量（拆串单段可被 parse_realtime_fields/parse_tencent_batch_data 直接解析，已单测）。② `hot-stocks-scan` 内存缓存 TTL 15s→45s：前端 30s 轮询下单用户 15s 永不命中（每轮全量重扫 120 只行情+资金流+评分），45s 交替命中、重扫减半。③ 该接口里 `save_stock_industry`/`save_predictions` 同步写库包 `asyncio.to_thread`，写锁等待不再冻事件循环。验证：重启后日志 `[初始化] to_thread 线程池已扩容: max_workers=48`，fund-flow 连续 6 轮 0.010~0.031s；扫描减请求效果看下一交易日日志的 `[趋势扫描] 批量行情预取：N/总数 只单码行情可复用`（周末无扫描）。
- **冷算秒级的接口不能被 10s 默认超时当成"报错"（2026-10-27）**：`/api/recommend-excess?months=6` 冷算单进程实测 **7.4 秒**（235 条推荐 × 6 个月全范围等权基准；代码注释里原来的"3.8 秒"是早期数据量，已作废），**并发下实测 14.4 秒**（09:2x 抓到一次 `cached=False` 的请求耗时 14393ms）。缓存是进程内 `_EXCESS_CACHE` + 30 分钟 TTL，所以**不需要重启服务，光 TTL 过期就足以让下一个打开页面的人撞上 10s 默认超时**（10-27 08:45 手机实拍红字"超额没算出来：请求超时（10s）"，而服务端其实随后算完并缓存，几分钟后测同一接口 3ms、数据完整）。修法两条：① `TabBacktest.loadExcess()` 单独 `timeout: 30000` + 失败自动重试一次；② scheduler 启动预热 `_prewarm_excess` 调 `routes.prewarm_recommend_excess()`，日志判据 `[预热 HH:MM:SS] 可执行超额缓存完成（冷算 X.Xs）`。
- **`apiFetch` 只在网络错误/超时/401 抛异常，HTTP 5xx 是 resolve 一个 `{detail}` 对象**（2026-10-27 桩测实锤：桩一个 500 只发出一次请求、页面也没有红字）。所以"重试 + 报错"不能只写在 `catch` 里，必须自己判 `d.success && d.data`；否则 `excess` 被塞 `undefined`，标题会永远挂着"正在算（冷启动约 8 秒）…"骗人——比报错更糟。
- **同一页里 `.bt-ex-table` 类名被两块复用**（可执行超额 + 因子体检），自动化断言必须按 `summary` 文本定位到具体那块，否则会拿体检表误判成"超额渲染出来了"。
- **`usePolling` 的启动契约（2026-10-27 修）**：`start()` 原来只能靠调用方自己调，**忘了就静默不轮询**——页面看起来只是"没数据"，接口侧完全正常。10-24 的轮询治理收尾（提交 `2c66dc0`）把 `IndexBar` 与 `TabApiUsage` 从裸 `setInterval` 迁过来时两处都漏了 `start()`，于是顶部指数条从那天起一直显示 `--`（`/api/market-index` 实测 0.01s 返回正常数据），接口用量页也不再自动刷新。现在的契约写在 `usePolling.js` 文件头：**不传 `immediate:false` = 挂载即轮询，由组合函数自己在 `onMounted + nextTick` 兜底启动**（`start()` 幂等，组件自己调过也不会重复跑）；只有"要等首屏数据/登录态就绪再开始"的才传 `immediate:false` 并显式 `start()`（现存 7 个调用方都是这种，行为不变）。新增 Tab 时优先复用兜底，别再手写 start。
### 页面加载耗时探针（2026-10-30，未提交）
- **目的**：用户要在页面上直接看到"这次切页到底慢在哪"，把"接口本身慢"与"隧道/传输/排队慢"分开，再据此定点优化，而不是凭感觉改超时。
- **后端只加一个响应头**：`server/app/main.py` 的 `_config_reload_middleware` 里用 `time.perf_counter()` 包住 `call_next`，写 `X-Process-Time`（毫秒，取整）。`CORSMiddleware` 的 `expose_headers` 已加该头——不 expose 浏览器 JS 读不到。只加头，不改响应体、不额外查询、不落库。
- **前端探针 `client-vue/src/utils/perf.js`（纯内存）**：`apiFetch` 每次请求 `beginRequest(url)`、`finally` 里 `endRequest(token, {ms, serverMs, status, ok})`。口径如下，改之前先看清每一条都是踩过的坑：
  - 只记 `/api/*` 与 `/eastmoney/*`；`/api/auth/*` 不计（会把"切页慢"混进"鉴权慢"）。
  - 切页记一次"本次加载"：`App.vue` watch `activeTab` 调 `startPage(tab, label)`，**必须 `flush:'sync'`**，否则子页自己的 active watcher 先发请求，首请求会漏进上一页的代数。收口＝这批请求全部返回且连续 **1.2s** 无新请求，硬上限 **30s**。
  - **1.2s 空闲宽限不计入总耗时**（用最后一个响应到达的 `lastEndAt` 算），否则每页凭空多 1.2s（首版实测 3.91s vs 实际 2.41s）。
  - 最后一帧渲染只补 **<300ms** 的差额：后台标签页 `requestAnimationFrame` 会被节流到 1s 以上，不设上限会把总耗时算成几秒。
  - `gen`（切页代数）防止上一页的迟到响应写进新页；`pending`（在途计数）防止慢接口被空闲计时提前收口。
  - `startWaitMs` = 切页到第一个请求发出；≥300ms 时展示条提示"页面代码下载/上页轮询"——这是首屏慢的第三类原因，既不是接口也不是隧道。
- **展示 `components/LoadTiming.vue`**：页头下方常驻一条折叠行 `本次加载 X.XXs · N 个请求 · 最慢 /api/xxx x.xxs（服务端 x.xxs）`；点开是逐请求表格（接口 / 发出偏移 / 总耗时 / 服务端 / 失败状态 / "传输·排队"差额，差额 ≥400ms 才显示）。手机 ≤620px 折叠行隐藏服务端小字（展开后仍逐条可见），不靠省略号藏内容。
- **实测（10-30 15:31 重启后，Playwright + xiaoming，420×860 与 860×900 两档，每页多次）**：行动台 0.21～2.34s（慢的那次是 `/api/action-desk` 冷算）、配置页 0.57～1.39s（服务端占绝大部分 0.55～1.37s）、推荐 0.21～1.01s（`/api/recommend-batches` 服务端仅 0.01～0.05s，差值在传输/JSON 解析）、行情 0.13～5.75s（其中一次 `/api/market-predict` 服务端 5.38s，属缓存过期后的冷算）、接口用量 0.02～0.10s。
- **探针暴露出的三大瓶颈（2026-10-30 当天已修，见「页面 2s 内专项」）**：`/api/settings` 冷路径（重启后首开 curl 实测 **27.8s**、TTL 过期 5.35s）、`/api/hot-stocks-scan` 缓存过期冷算（8.71s 实拍）、`/api/market-predict` 冷算（5.38s）。瓶颈全部在服务端冷算，不是传输。
- **本探针不覆盖**：页面 JS chunk 下载耗时（只在 `startWaitMs` 中间接体现）、`/api/auth/*`、图片与静态资源。

### 页面 2s 内专项（2026-10-30，未提交）
- **背景**：耗时探针上线当天用户实拍筛选页 8.81s（`/api/hot-stocks-scan` 服务端 8.71s），要求所有页面加载 ≤2s。逐段打点后定位出三类根因，全部是**服务端冷算**，与隧道无关。
- **根因①（影响面最广）**：`universe` 两层范围缓存与 `liquidity._STATS` 的 TTL 都是 600s，但调度器只在**启动**预热一次——重启约 10 分钟后过期，下一个撞上的请求（批量扫描的 `selectable_prefixed`、配置页、海选）要再付 3～8s 冷算。**修法**：调度器 `_keepwarm_universe` 改常驻线程，每 540s 后台 `liquidity.stats_map(force=True)` + `universe.refresh_caches()`（新函数：先算好再原子换入，与 `invalidate_cache` 的"先清空再现算"不同，刷新窗口内请求继续用旧值，永不撞冷路径）。
- **根因②**：`/api/hot-stocks-scan` 的 45s 缓存一过期，下一个请求就同步付全量重扫（实测冷 2.2s、过期叠并发 8.7s、离群 53.9s），且没有 singleflight，30s 轮询叠并发会重复扫。**修法**：陈旧兜底（stale-while-revalidate）——缓存过期但未超 `_HOT_SCAN_STALE_MAX=600s` 时**立即返回旧数据**，由 `_spawn_hot_scan_refresh` 起后台线程刷新（20s 节流；子线程 `asyncio.run` 安全，因为扫描的网络调用全走 requests+to_thread）；只有完全无缓存或 `force=1` 才同步算。顺带加了阶段耗时日志（`[批量扫描] 阶段 候选+范围/行情批量/附加数据(含 7 项明细)/评分/落库`）。
- **根因③**：`/api/settings` 每次请求都现算四项口径摘要（数据范围/选票/预览一致性/停同步数），重启后首开 27.8s。**修法**：摘要整份缓存进 `settings_preview`（`compute_summary/summary_snapshot/summary_age/refresh_summary_async`），`/api/settings` 只读快照、超龄（>540s）触发后台重算；改「选股范围」组配置后由 `app_settings.set_value/reset_value` 触发后台重算（旧值在重算完成前继续兜底，界面数字最多旧几秒）。
- **启动预热补齐**：调度器新增 `_prewarm_hot_scan` 线程——①用 `load_user_scan_pool()`（无参=全部用户池并集，与前端传参同源）预扫一次批量扫描，重启后筛选页首开即命中缓存；②`build_action_desk(user_id=1)` 预热行动台公共缓存（持仓段按用户现查本来就轻）。
- **market-predict** 同样加了陈旧兜底（`_MARKET_PREDICT_STALE_MAX=600s`、30s 节流），60s TTL 过期后不再白付 500 只行情重扫（实测 5.38s 那次）。
- **实测（10-30 17:06 重启后，xiaoming）**：重启后**首开**——筛选页 0.05s、配置页 0.04s、行动台 0.27s、行情预测 1.30s、推荐 0.09s、接口用量 0.03s，全部 ≤2s；TTL 过期场景（人为等 50s/65s）——扫描 0.05s、预测 0.14s（陈旧兜底生效，后台刷新完成）；页面级 Playwright 两档视口 0.03～0.67s。自测 `analysis_out/page2s_selftest.py` **12/12**（refresh_caches 只数一致 1058、摘要往返、节流不再起线程、常量齐全）。
- **边界（如实）**：`force=1` 强制重算仍是一次 ~2.9s 的同步冷算（前端只有手动"立即刷新"类操作会带 force，正常浏览不会）；陈旧兜底期间页面数据最旧 10 分钟（扫描/预测本来就是轮询画面，可接受）；保活刷新每 9 分钟在后台花 ~0.7s，不占请求路径。

### 筛选页「自定义最低分」默认值走配置页（2026-10-24）
- **现象与根因**：用户把「过滤模式＝自定义最低分」的输入从 60 改成 65，刷新后又回到 60。根因不在扫描接口——`TabScan.vue` 的 `onMounted` 每次都 `await loadTabConfig()`，该函数无条件把 `filterMode/customMinScore` 写成 `/api/tab-scan-config` 的默认值；用户的输入从未被保存。轮询只替换 `scanResults`，所以"过一会儿变回去"实际发生在刷新/重新挂载时。
- **口径（用户指定，不是我的选择）**：用户明确"把 `config.py` 里默认 60 去掉，直接在配置页配置"，并把筛选页那个数字定性为"显示 + 临时过滤"。所以**删掉 `config.TAB_SCAN_DEFAULT_MIN_SCORE`**，改由 `app_settings` 注册项 `tab_scan_default_min_score` 单一管理：group=`股票筛选页`、`kind=int`、0~100 分、step 1、出厂 `default=60`、`live=True`（即时生效，无需重启）。
- **后端读路径**：`app_settings.default_value()` 扩展为「有 `cfg` 读 config.py，无 `cfg` 读 SPEC 的 `default`」——纯界面项不必再为了一个常量污染 config.py；`/api/tab-scan-config` 里 `defaultMinScore` 改为 `A.value('tab_scan_default_min_score')`，**每次请求现读**（覆盖值优先，没有则默认 60）。该注册项**不声明 `impact`**，`TabSettings.vue` 对无 `impact` 的项跳过 `/api/settings/preview`，避免出现"1094 → 1094、+0"的假结论。
