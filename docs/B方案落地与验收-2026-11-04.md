## 二、P0-B 具体做法

- `GET /api/daily-reviews?page=N`，固定 1 条/页，**不暴露 `page_size` 自由参数**（公开隧道接口若允许任意 `page_size`，缓存会被撑成无数份 —— 11-04 复盘缓存被 `days` 挤爆是同一个教训）。
- `page=0` / 不传仍返回全量，老脚本零改动；响应在旧 `success/data` 之上**只增不减**追加 `page/pageSize/total/totalPages/recentFocus`。
- 一次查库把「全量 + 每页」全部预序列化 + 预压缩进同一份 SWR bundle（30 页约 1MB 内存，换翻页零计算），不把「每请求重压」请回来。
- 前端 `TabReview.vue` 按页取、`totalPages` 用后端值、翻页带响应竞态守卫。**易漏点**：`loadFocusQuotes` 原本取 `reviews.slice(0,3)` 的明日关注，分页后前端只剩 1 条会静默丢行情徽章 → 改由后端下发同口径 `recentFocus`。

## 三、P3 为什么没改架构（复查纠正了一个旧判断）

读代码发现：`core/scheduler.py` 的定时任务在独立线程里各自 `asyncio.run(...)` 建**临时 loop**，`to_thread` 用的是临时 loop 自己的 executor —— **本来就不共享 uvicorn 主 loop 的 48 线程池**；预热项也是独立 `threading.Thread`。真正共享主池的长任务只有 API 触发的趋势后台重扫 `trend._start_bg_rescan()`（`asyncio.create_task` 挂在主 loop）。

而 `_get_scan_lock()` / `get_scan_semaphore()` 是**按 loop 重建** `asyncio.Lock`/`Semaphore`（防「锁不跨 loop」），把重扫协程搬去独立 loop 会让主 loop 与后台各持一把锁、单飞闸门失效 ⇒ **风险大于收益**。

于是改做待办里要求的并发压测反证：借重启后预热链活跃窗口，200 秒内每秒采样 4 个端点，共 **764 条**（`server/analysis_out/p3_concurrency_probe.json`）。

| 端点 | 预热期 wall p50/p95/max | 静默期 wall p50/p95/max | 静默期 XPT p50/p95/max |
|---|---|---|---|
| health | 2.9 / 21.2 / 2027.5 ms | 2.2 / 4.7 / 6.6 ms | 0 / 1 / 3 |
| reviews?page=1 | 3.3 / 16.5 / 123.0 ms | 2.8 / 4.4 / 8.4 ms | 1 / 2 / 4 |
| reviews?page=2 | 3.1 / 28.7 / 140.0 ms | 2.7 / 5.1 / 7.2 ms | 1 / 2 / 4 |
| market-index | 3.0 / 53.6 / 360.8 ms | 2.3 / 4.2 / 7.3 ms | 1 / 2 / 2 |

`XPT > 100ms` 仅 **5/764（0.65%）**，全部集中在预热链活跃的 0～83 秒；静默期所有接口 p95 ≤ 5.1ms、XPT ≤ 4ms。44～53 秒 `health` 三次 1.2～2.0 秒长尾里有一次 `XPT 仅 1ms`，说明请求在到达服务前排队（GIL / accept 层），不是接口计算慢。**这是偶发长尾，不是系统性饱和。**

> 将来若要做的**前置条件**：先把单飞闸门换成进程级 `threading` 闸门保证跨 loop 互斥，再谈专用 executor；只换池子会让并发扫描失控。
