# A股短线交易台（行情 · 选股 · 推荐 · 持仓 · 复盘 · 推送）

最初它是个"A股实时行情查询"，现在是一整套围绕短线决策的工作台：盘中出信号、盘后做复盘、
选票口径可以在界面上改、每天的决策现场会落库供以后回放。
后端 FastAPI + SQLite（单机自托管，无外部数据库），前端 Vue 3 + Vite，企业微信推送。

## 一页速览

| 分组 | 页面 | 回答的问题 |
|------|------|------------|
| 首页 | **行动台** (`tab-desk`) | 现在这个时刻该做什么：买入区/持仓处理/环境否决，情绪周期直接参与硬拦（盘中数据降级时只提示不拦并标注沿用时间；收盘后展示**今日收盘定版**——收评未生成先用今日快照顶住，不拿昨日充今天）；另有**主题链温度卡**（人形机器人/商业航天/算力三条自建等权链，按近 3 日涨幅自动选"当前最热链"并可在卡上切换：温度 0~100 + 距高点回撤，只提示"减一部分"，不判顶） |
| 盘面 | 实时行情 · 股票筛选 · 趋势发现 · 资金流向 | 价、量、形态、板块资金在说什么；筛选页顶部标数据口径时刻（`X-Scan-As-Of`），名称列挂吸筹/出逃/龙虎榜信号徽标 |
| 决策 | 智能推荐 · 持仓管理 · 模拟交易 | 推哪 3 只（含买卖点与买入时机）、手里的怎么处理、不改真钱先验证想法；模拟持仓标题行带盈亏概况条（盈利/亏损只数与占比） |
| 复盘 | 每日收评 · 自动优化 · **口径与开关** · **回测曲线** | 昨天推得对不对、权重该怎么调、六条选股口径与各项阈值现场改；回测曲线首屏默认画**能操作的那条**（尾盘买·封板剔除）并把"按推荐执行/排板上界"并排做对照，配**回撤（水下曲线）**与同期等权背景，回测页模式榜带运行天数与名次变化（T+1 样本 ≥5 才参与排名） |

  —— 它决定"日K同步清单"和一切覆盖率的分母。
- **选票范围 1094** = 在数据范围之上再叠 近 20 交易日日均成交额 > 0.8 亿、日均换手率 > 1.5%、股价 > 3 元
  —— 它决定海选百分位排名、智能推荐入口、趋势扫描、盘中扫描与推送。
- 唯一出处 [`server/services/data/universe.py`](server/services/data/universe.py) 与
  [`server/services/data/liquidity.py`](server/services/data/liquidity.py)；六条各有独立开关，
  关掉任何一条都会在页面上实时报"放回多少只"。**别让流动性条件去管同步清单**——
  缩量票今天进清单明天出清单，历史序列就会挖洞，MA60 / 60 日高点 / RPS 全被洞污染。
- **本地日K 的覆盖自检（2026-11-02 加）**：主路是盘后腾讯收盘快照（零登录），baostock 只当备路与
  历史回填。每次同步收尾自动跑 `kline_history.coverage_report()`：以库里最新一天为右端往回取 20 个
  **日历交易日**，库里整天没有的行当场点名（只看"库里出现过的日期"永远看不见整日缺失），覆盖只数
  跟**窗口中位**比而不是最大值（10-16 之前 5222 只的宽口径日子会把正常天全误报成缺口）。手工补某一天
  用 `python scripts/backfill_kline.py --mode sync --fill-dates YYYY-MM-DD`，**非交易日会被交易日历
  当场拦下、不发起一次登录**——11-02 曾对着周六的 2026-10-31 空跑 2464 次查询 / 4 次登录 / 438s 全零，
  而 baostock 的登录频率本身就是它的风控信号。判据自测 `server/analysis_out/selftest_kline_coverage.py`。

## 快速开始

```bash
cd server
start.bat            # Windows 双击即可：构建前端 → 装依赖 → 起 FastAPI（端口 3003）
```

`start.bat` → `start.py` 的顺序是：① 构建前端（首次 `pnpm install`，之后增量 `pnpm run build`）
② 检查 Python（`python3` / `python`）③ 装/更新 `requirements.txt`（清华源失败自动回退默认源）
④ 启动 `run.py`（uvicorn，`reload=True` 监视 `app/`、`services/`、`db/`，改这些目录下的 .py 会自动重载）。

> ⚠️ **生产/守护部署不要用 `run.py`**：本机 7×24 由隧道守护（仓库外 `D:\tools\cf\tunnel_watch.py`）看护，
> 守护按自己拉起时的命令行（`-c "import uvicorn; ... reload=False"`）判断后端活没活，
> `run.py` 的 reload 形态守护认不出 → 误判"没在跑"→ 再拉一个 → 抢 3003 端口。
> 手动起服务用 `server/analysis_out/serve_3003.py`（reload=False，与守护同口径）。
>
> ⚠️ **改完代码要让后端重启才能生效，但看护拉起的进程会话杀不掉**（任务计划以 SYSTEM 运行，
> 非管理员 `taskkill` 直接"拒绝访问"；此时自己再起一个会因 3003 被占而 `[Errno 10048]` 退出，
> 日志照样打印"启动完成"，看着像重启成功、实际还在跑旧代码——2026-10-23 晚踩过）。
> 正确做法：写标志文件 `server/data/backend_restart_requested`，看护下一轮（≤5 分钟）读到就
> 自己杀进程树→拉起新代码→删标志→推企微；工作日 09:10~15:10 之间只推迟不重启，避免打断推荐批次。
> 重启后务必核对"接口返回里新字段有没有"，不要只看 `/api/health` 200。
>
> ⚠️ **日志打印本身不能成为故障点**（2026-11-02 加）：守护把 stdout 重定向进
> `server/server_supervised.log` 的那条管道是 **GBK**，于是一条带 `⚠️` 的 `print` 会抛
> `UnicodeEncodeError`，把打它的任务一起打死——`[推荐模式]` 标签日志 10-26 起崩了 16 次就是这样。
> `app/main.py` 入口已加兜底：探测到 GBK 家族编码就把 stdout/stderr `reconfigure` 成 UTF-8
> `errors='replace'`（UTF-8 环境不动它，兜底自身包在 try 里不影响启动）；`analysis_out/backfill_kline.py`
> 同口径。**这条兜底要下次重启才进线上进程**，反证/正证自测：`cd server && python analysis_out/selftest_log_encoding.py`。
> 同一入口还掐了另一类噪声：`Exception in callback … _call_connection_lost … [WinError 10022]`
> 是 Windows proactor 在客户端硬断开时的固有行为，日志里 160 条签名完全一致，只会把真故障埋掉——
> 过滤器只掐"两个标记同时命中"这一种，其余 asyncio 记录照常放行（自测拿真实日志逐条回放验过）。

访问 <http://localhost:3003> 使用应用；API 文档在 <http://localhost:3003/docs>。

### 首次使用：注册账号

系统是多用户（持仓、股票池、推送绑定都按账号隔离），**首次打开会进登录页**：

1. 在登录页切到「注册」，填用户名 + 密码（≥6 位）
2. **第一个注册的账号会天然继承库里已有的历史持仓**——存量持仓迁移时被挂在 `user_id=1`，
   而首个注册者的自增 id 正好是 1（顺序约束写在 `services/support/auth.py`：先迁库后注册会让
   存量持仓变成无主孤儿）。之后注册的账号从零开始，彼此看不到对方的持仓
3. 登录页下方会列出已有账号，点一下即自动填用户名
4. 「口径与开关」子页里能改配置的是**最早注册的那个账号**（`users` 表没有角色列，
   只能这样定管理员；想指定别人就改 `SETTINGS_WRITE_USER_IDS`）

不想开放自助注册 → `AUTH_ALLOW_REGISTER = False`；想整体关掉登录（回到单用户）→ `AUTH_ENABLED = False`。注册关闭时，登录页不会渲染「登录 / 注册」切换条（只剩提交按钮），避免看起来像两个登录。

### 手机访问

本机是内网机器，手机在外面打不开 3003。做法是用 cloudflared quick tunnel 把 3003
映射成公网地址，并由守护脚本在隧道断开时自动重建（**重建必然换网址**，换址会通过企微推送，
每天限 3 条以免网络抖动时刷屏）。守护与冷却策略在仓库外（`D:\tools\cf\tunnel_watch.py`），
后端只负责把"后端没起来"和"公网不通"分开判断，避免误换址。

### 9. AI 选股推荐策略（2026-06-30 优化）

针对“AI智能选股推荐”板块，系统采用了一套结合量价协同、龙头溢价、主力资金和骗线过滤的综合评分算法。

#### 9.1 核心评分因子（13因子，总分 100）

> **2026-06-30 升级**：从 8 因子扩展到 9 因子，新增「主力净流入」因子；涨停质量从 2 档细化为 5 档。`max_possible` 改为从 `STRATEGY_SCORE_VALUES` 动态提取各因子最大档位分值计算，避免硬编码导致新增因子后归一化错误。
>
> **2026-07-06 升级**：从 9 因子扩展到 10 因子，新增「股东人数筹码集中度」因子（`holder_structure`）。数据源为东方财富 datacenter API **`RPT_HOLDERNUMLATEST`**（"最新股东户数"聚合表，每只股票只留最新一期；**2026-10-31 换表**——原 `RPT_F10_EH_HOLDERNUM` 的 `ISNEW` 列已下线、请求返回 code 9501，任务连续多日"数据为空,跳过"，`stock_holder_num` 一直是 0 行），18:00 定时拉取存 DB（**2026-10-19 起改周一/周四，财报季 1/3/4/7/8/10 月恢复每日**——取的是最新一期，披露后就不再变，每天重拉全市场只是把同样的行搬一遍），评分时从 DB 缓存批量查（不实时拉取，月度数据无实时需求）。权重 1.2（月度数据有滞后，略高于基础 1.0）。
>
> **2026-07-16 升级**：从 10 因子扩展到 11 因子，新增「RPS 相对强度」因子（欧奈尔体系核心，`rps`）。数据源为腾讯前复权日线，盘前/手动批量预计算"全市场区间涨幅→百分位排名"写入 SQLite `rps_cache` 表，盘中扫描/分析直接读缓存（秒级），无缓存降级中档分 7 分不拖累总分。权重 1.1。详见 [第 9.2 节](#92-rps-相对强度因子欧奈尔核心p0)。
>

##### 9.1.3 大盘下跌门槛强化（2026-07-08，2026-07-14 调整作用范围）

#### 9.2 选股硬性过滤规则

在生成推荐名单前，系统会执行以下硬性拦截，确保“实战可操作性”：

- **基本面安全**：自动过滤名称含 `ST` 或 `退` 的风险股。
- **成交真实性**：**分级软惩罚**（非硬过滤）。涨停股天量开板（vol>8x+outer<45%）重罚-5分，放量偏弱（vol>5x+outer<48%）轻罚-3分；非涨停股放量外盘不占优时扣-5分。正常封板不罚。
- **拥抱龙头**：**完全取消**对高涨幅股的硬过滤。允许涨停股入选，旨在发掘次日高开溢价或龙回头机会。

#### 9.3 P2/P3 优化说明（2026-06-30）

承接 P0（板块效应/连板梯队）/ P1（主力净流入/涨停质量），P2/P3 进一步补齐筹码结构、量价形态、动态阈值、行业中性化四项：

**筹码结构修正系数（`trend.py _calc_chip_factor`）**
无真实 CYQ 筹码数据，用 4 个代理指标组合刻画筹码结构，作为乘性修正系数叠加到趋势总分（钳制 ±8%）：
- 子项1 成本压力位：现价 vs MA60/MA120（双线上方 +3% / 双线下方 -5%）
- 子项2 换手率松动度：1-3% 筹码锁定 +2% / >15% 筹码松动 -2%
- 子项3 主力筹码动向：主力净流入占比 ≥3% 吸筹 +3% / ≤-3% 派发 -3%
- 子项4 量能稳定性 CV：≤0.3 沉淀 +2% / >0.8 紊乱 -2%

** 量价6形态分类（`services/pattern.py detect_volume_price_pattern`）**
识别 6 种互斥量价形态（优先级：突破类 > 滞涨/背离类 > 回调类 > 横盘类），作为乘性修正系数（±4%）：
- 放量突破 +4% / 倍量反包 +3% / 缩量回调 +2%
- 放量滞涨 -4% / 量价背离 -3% / 缩量横盘 -1%

**动态阈值（`trend.py _classify_market_regime` + `_get_dynamic_thresholds`）**
按 `market_regime(bull/bear/range) × pattern` 三级优先覆盖 D1/D3/D4 扣分阈值（精确匹配 > regime 默认 > 全局默认）：
- 牛市：放宽乖离惩罚（追高容忍），收紧破位扣分
- 熊市：收紧乖离/回撤档位（追高风险大、回撤容忍收紧）
- 形态特化：放量滞涨/量价背离/缩量横盘扣分加重
- 大盘状态由 sh000001 现价 vs MA20 + 当日涨跌联合判定

**行业中性化（`strategy.py apply_industry_neutralization`）**
对 `calc_stock_score_v2` 输出的 `total` 按行业 P20/P80 分位数做 ±2 后处理调整（见 §9.1 末行），三层调用对齐。单行业样本 <5 不调整。

### 9.2 RPS 相对强度因子（欧奈尔核心，P0）

**定位**：选股胜率提升的 P0 项（性价比最高）。RPS 衡量"个股区间表现强于全市场多少比例的股票"，是欧奈尔 CAN SLIM 体系识别领涨龙头的核心指标。弱市里 RPS 高的票往往率先走强，是"顺势而为"的量化落地。

**算法**
1. 全市场 A 股代码：东方财富 clist（`m:0+t:2,m:1+t:2`）分页拉取（接口单页硬上限 100 条，需翻页合并去重，全市场约 1843 只）。
2. 区间涨幅：腾讯前复权日线（K 线）`param={symbol},day,{START},{END},{limit},qfq`，取区间起点/终点收盘价算 `(c1-c0)/c0`。
   - **为什么不走东方财富 clist 区间参数**：实测 push2delay/push2 的 clist 在带 `k1/k2/k3` 时 `f3` 仍返回当日涨跌幅（接口不支持区间统计），故改用 K 线计算区间涨幅，最可靠。
3. 百分位排名：`RPS = 排名 / (样本数-1) × 100`。RPS 90 = 强于 90% 个股。
4. 多周期：`RPS_PERIODS=[50,120,250]`（月/季/年），主评分用 `RPS_PERIOD_DAYS=120`。

**缓存与调用**
- 盘前/手动触发 `refresh_rps(period_days)`，线程池（`max_workers=10`）并发拉全市场 K 线（1843 只约 30–40 秒），结果写 `rps_cache` 表（主键 `(period, symbol)`，存 `rps` + `interval_change`）。
- 盘中扫描/分析经 `get_rps_map()` 直接读缓存（秒级），无缓存降级中档分 7 分不拖累总分。

**新增接口**
- `GET /api/rps?period_days=120&top_n=50`：RPS 强势股榜（降序前 N，含名称/区间涨幅），供前端 `TabStrategy` 展示。
- `POST /api/rps/refresh?period_days=120`：后台触发全市场预计算，立即返回 accepted，约 30 秒后 `/api/rps` 可查。

**配置项（`app/config.py`）**：`RPS_ENABLED / RPS_PERIOD_DAYS / RPS_PERIODS / RPS_CACHE_TTL / RPS_MIN_SAMPLES / RPS_TOP_N`，以及评分阈值 `STRATEGY_SCORE_THRESHOLDS['rps']`、分值 `STRATEGY_SCORE_VALUES['rps']`、权重 `DEFAULT_WEIGHTS['rps']=1.1`。

### 9.3 风控止损与估值分位过滤（P2a / P2c，2026-07-16）

**P2a 风控止损输出（`services/risk_control.py`）**——为每只被推荐/被查看的股票输出一套"可执行的风控结论"，纯函数（零 IO）可在扫描循环内逐股同步调用，不增加网络请求：

- **止损价 `stop_loss`**：基于当日振幅（波动率代理）动态缩放止损幅度 = `clamp(振幅% × 1.5, 4%, 12%)`；停牌/无振幅数据给中性默认 6%。低波动股止损窄、高波动股止损宽。**V4.6（2026-10-28）**：角色体系整体下线，止损只叠加位置倍率（低位放宽 20%、高位收紧 20%），不再有龙头/跟风角色倍率；`risk_note` 只写"高位止损 X%"或"止损 X%"。
- **买卖点 `buy_sell_points`**（V4.6 位置感知版，2026-10-28 去角色）：止盈幅度 = 基础比例 × 位置倍率 × 评分倍率，封顶 15%。位置判定优先 `trend_details.positionPct`（精确年度分位），fallback `base_scores['position']`。涨停股基础比例固定 4%（原七档 2%~7% 的中值，**占位不是验证结果**，封板强度类数据补齐前不分档）；非涨停股按振幅 6%/5%/4%/3% 止盈、3%/2.5%/2%/1.5% 买入回撤档。输出含 `sellPct` 与 `expectationNote`，不再有 `stockType`。
- **风险等级 `risk_level`**（low / mid / high）：基础由综合评分决定（`<55→high`，`<65→mid`，否则 `low`）；叠加高危信号（估值极端高估 / 龙虎榜净卖出 / 股东户数环比 ≥10% 散户化）至少升 `mid`，高风险不可被降级。
- **仓位建议 `position_suggest`**：low→可重仓(≤80%)，mid→半仓(≤50%)，high→轻仓(≤30%)。
- **一句话 `risk_note`** 直连前端展示。注入点：单股分析端点、full 端点、扫描端点、智能推荐（推荐卡片内嵌"🛡️ 风控建议"区块）。

**P2c 估值分位过滤（`services/valuation.py`，18:10 盘后更新；2026-10-19 起仅交易日——周末没有新收盘价，拉回来是同一份）**：

### 9.4.1 回测成交口径：封板判定 v2（2026-10-20）

回测曲线里"涨停买不到、跌停卖不掉"这两条，直接决定回撤数字可不可信。旧实现有两处不真实：

- 买入侧把「收盘价==当日最高价 且 涨幅≥97%限额」一律当作封死剔除——**盘中炸过板、尾盘又回封**的票
  其实存在过低于涨停价的成交，被一起剔掉了；而且用百分比近似涨停价，低价票四舍五入后判错。
- 卖出侧「一字跌停卖不掉就顺延」**只对开盘卖生效，尾盘卖连检查都没有** —— 等于假设跌停也能按
  收盘价卖掉，回撤被系统性低估。

v2 改判「**当日是否存在突破价成交**」，价位按前收精确算（`round(前收×(1±板幅), 2)`，创业板/科创板 20%）：

| 判据 | 买入（涨停票） | 卖出（跌停票） |
|---|---|---|
| 可交易 | 当日最低价 < 涨停价 → 存在过可买价 | 当日最高价 > 跌停价 → 存在过可卖价 |
| 真封死 | 最低价 ≥ 涨停价（一字/T字）→ 剔除 | 最高价 ≤ 跌停价 → **顺延到下一根K线**，open/close 两种卖法都判 |

两档判据必须分开，不能合成一个变量：`sealed_at_close`（收盘仍钉在涨停价，决定「次日竞价买」分支，
卡片对涨停票的本意就是竞价关注）与 `sealed_hard`（全天没低下去过，才允许剔除）。
实现时把 auction 分支买入后的两个标记都清空——只清一个会让竞价买进来的票被下一道剔除再杀一遍
（自测抓到过：auction 笔数从 101 掉到 60，和尾盘口径一模一样）。

独立开关（都在覆盖表「回测成交口径」组，热改不重启）：`REC_SIM_BOARD_PRICE_V2`（判据版本）、
`REC_SIM_DEFER_LIMIT_DOWN`（跌停顺延是否也管尾盘卖）、`REC_SIM_BOARD_EPS`（价格容差）。
**两个都关掉即逐字节回到改造前的曲线。**

真实流水上的影响（2026-07-18~10-19，124 条推荐，10 万本金）：

| 口径 | 旧收益 | 新收益 | 旧回撤 | 新回撤 | 旧笔→新笔 |
|---|---|---|---|---|---|
| 低吸成交·开盘卖 | +12.10% | +12.10% | -12.1% | -12.1% | 119→119 |
| 低吸成交·尾盘卖 | -4.01% | **-4.58%** | -24.3% | -23.5% | 119→119 |
| 次日竞价买·开盘卖 | +0.60% | +0.60% | -16.2% | -16.2% | 101→101 |
| 次日竞价买·尾盘卖 | -13.77% | -12.39% | -28.3% | -27.0% | 102→102 |
| 尾盘买入·开盘卖 | -24.24% | +5.33% | -29.3% | -17.3% | 60→**118** |
| 尾盘买入·尾盘卖 | -41.74% | -9.43% | -44.4% | -27.4% | 60→**118** |

读这张表要注意的边界（不是 bug，是口径性质）：**尾盘买入那两行的改善是"上界"，不能当作策略变好**。
它纳入了 57 笔炸板回封的票，成交价仍按当日收盘价（=涨停价）算——已是纳入情形里最差的价，
但"排队一定成交"是日线无法验证的假设，真实结果落在旧口径（全剔，下界）与新口径（全收，上界）之间。
卖出侧的跌停顺延在这个窗口只命中 1 笔，所以回撤变化很小；而旧口径"跌停也能卖掉"的高估，
体现在那 1 笔从 -4.01% 变 -4.58% 的方向上。逐笔与汇总对照可用
`server/analysis_out/board_rule_v2_diff.py`，判据自测 `board_rule_v2_selftest.py`（23 项）。

### 9.4.2 回测仓位规则：风险预算与敞口上限（2026-10-20，默认关）

现行规则在 `rec_sim.run()` 里只有一行：`budget = cash / 当天要买的只数`——**满仓等分、不留现金缓冲**。
实测后果（7-18~10-19 窗口）：单笔占净值中位 32%、**最大 99.5%**，因为"当天只推 1 只"时一笔就押满
（低吸口径 2 天、竞价口径 12 天、尾盘口径 16 天如此）。而按逐笔分布算的连续凯利只有 2.0%，
满仓比它高一个数量级——12%~44% 的回撤主要来自这里。

现在把仓位规则做成可切换参数（覆盖表组「回测仓位规则」，全部热改）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `REC_SIM_SIZING_V2` | **False** | 总开关。关掉＝上面那行老规则，曲线逐字节不变 |
| `REC_SIM_RISK_PER_TRADE` | 1.5% | 每笔只让账户承担这么多风险，仓位＝它 ÷ 止损幅度 |
| `REC_SIM_STOP_PCT` | 8% | 折算用止损幅度（线上三套止损已统一到 `exit_rules`，默认影子、见 §9.6；回测仍按固定 8% 保守折算） |
| `REC_SIM_MAX_POSITION_PCT` | 25% | 单票占净值上限，专治"当天只 1 只就押满" |
| `REC_SIM_MAX_EXPOSURE_PCT` | 60% | 同日总敞口（持仓＋当天新买单），剩下留作现金 |

三条约束**各自独立生效**（可只开单票上限看效果）。⚠️ 单位有个坑：覆盖表 `value()` 返回的是
**界面单位（百分数）**，`scale=100` 会把 config 里的 0.015 变成 1.5，所以代码里 `risk÷stop` 无量纲直接是仓位比例，
而 `cap`、`exposure` 要除以 100——`position_sizing_selftest.py` 专门钉了这条。

同一批真实推荐、同一套撮合（封板判据 v2）下的对照：

| 口径 | 满仓 收益／回撤 | 风险预算B 收益／回撤 | 保守C 收益／回撤 |
|---|---|---|---|
| 低吸成交·开盘卖 | +12.10%／-12.1% | +8.19%／-7.2% | +6.93%／-3.4% |
| 低吸成交·尾盘卖 | -4.58%／-23.5% | **+4.49%／-6.5%** | +3.42%／-4.0% |
| 次日竞价买·开盘卖 | +0.60%／-16.2% | -7.05%／-7.1% | -7.22%／-7.2% |
| 次日竞价买·尾盘卖 | -12.39%／-27.0% | -9.25%／-11.9% | -8.94%／-9.6% |
| 尾盘买入·开盘卖 | +5.33%／-17.3% | +6.49%／-7.2% | +5.62%／-3.8% |
| 尾盘买入·尾盘卖 | -9.43%／-27.4% | **+2.93%／-7.9%** | +2.33%／-5.0% |
| **六档平均** | **-1.40%／-20.6%** | **+0.97%／-8.0%** | +0.36%／-5.5% |

结论要说准：**约束压掉的主要是波动，顺带把平均期望从负拉到正**。六档平均回撤从 20.6% 降到 8.0%（-61%），
平均收益从 -1.40% 升到 +0.97%（C 档 +0.36%、回撤只剩 5.5%）。但**不是全档都受益：六档里四档改善、两档变差**，
变差的两档恰好都是「次日开盘卖」（低吸·开盘卖 12.10%→8.19%、竞价·开盘卖 +0.60%→-7.05%）——
满仓时把钱全押在"开盘就兑现"上最赚，留 40% 现金就把这两档摊薄了。这正是
凯利的行为方式：期望越高越该重仓，期望接近零时重仓只是在放大噪声。**这是"10-24 之后要不要采用"的判据**，
不是现在就改线上：先跑对照，别拿 3 个月单窗口当定论。对照图
`docs/资金曲线-仓位规则对照.svg`，脚本 `server/analysis_out/position_sizing_compare.py`。

### 9.5 市场主线/支线板块（2026-10-22，行动台 sectors 卡，影子期）

`services/strategy/mainline.py` 把四路**已在内存/本地**的数据合成一份主线判定，
行动台在"短线情绪"下面渲染"🎯 市场主线"卡（顺序=先情绪→再主线→最后个股）。
**零新增外部请求**：涨停结构复用 sentiment 缓存（180s），板块资金走
`fundflow.peek_sector_flow()`（只读缓存/快照；另有 30 分钟节流的服务端保活

调度器是 asyncio.run 的一次性循环，所以保活里直接 await 扫描算完，不能依赖
"后台起算本轮返回 None"的页面式设计），持续性读本地日K×行业映射表。

- **五维评分**（各维在数据源内做分位归一——东财 f62/新浪 r0/旧快照三套绝对额不可跨源比）：

  ＋涨幅持续性 0.20（近 5/10 日成员交集·截尾均值·复利，`sector_persistence_daily`，
  09:05/20:25 预热）＋量能 0.10；情绪周期做市场级门槛（冰点/退潮主线门槛 +8）不做板块分。
- **分层**：主线 ≤2（分≥62 且最高连板≥2；与第 2 名断层≥10 只认一条）、支线 ≤5、
  退潮（昨日主线今日资金转负/梯队清零，绿色 chip）、无主线（最高分<42 → 给 reason，
  对应游资心法的空仓哨兵）。10:00 前不判、涨停池 degraded 只出候选、资金快照>2h 不判。
- **收盘定版（2026-10-23 晚）**：休市后不再按盘中闸门挂起——① 情绪走定版链（今日收评 →
  今日快照 `snapshot_final` → 最近收评），`final=True` 只改页面措辞、不给否决权；
  ② 主线用 `limit_pool_daily.raw` 重建当日 `leadSectors`（收评只存总量，没有板块清单），

## 技术说明

- 前端：Vue 3 + Vite（`client-vue/`），Vite dev 代理到后端 `/api/*` + `/eastmoney/*`；生产由后端挂载 `static/` 构建产物
- 后端：Python + FastAPI（`server/app/main.py`）
  - 腾讯财经API：获取股票实时行情和K线数据
  - 东方财富API：获取热搜榜/板块数据，并通过 FastAPI 路由 `/eastmoney/*` 代理推送给前端（统一使用 `requests + asyncio.to_thread`，避免 `httpx.AsyncClient` 直连 `push2.eastmoney.com` 的 Server disconnected 问题）
  - 人气榜API：`emappdata.eastmoney.com/stockrank/getAllCurrentList`（东方财富股吧真实人气榜，需 `httpx` 库 POST 访问，`requests` 会被服务器拒绝连接）
  - 人气榜熔断：`appdata` 是独立 scope，不受 push2 全域闸门连带停止；成功不关全域、失败只冷自己。热搜榜抓空时保留上一份缓存，不覆盖、不删当日快照；行情源被熔断、名称/价格缺失时，先用本地 `stock_basic_info` 补名称（零外部请求）、再用腾讯批量行情补价格（一次 60 只），避免空名让 ST/退市过滤失真、价格缩水或为 0。另注意 `ulist.np` 用 `fltt=2`，返回的 f2/f3/f4 已是真实数值，不能再除 100
  - 热搜榜备源：东财人气榜返回空时自动改用同花顺热股榜（`dq.10jqka.com.cn/fuyao/hot_list_data/out/hot_list/v1/stock`，`type=hour`，免登录、前 100 只带名称与名次，`Referer: eq.10jqka.com.cn`，120 秒缓存）；本轮用了谁记在 `hot_search_meta.source`（`eastmoney`/`ths`），`/api/hot_search_ranking` 一并返回
  - 接口用量登记：`api_usage._HOST_EXACT` 里没有的域名不会丢计数，但会挂到"其他"下、没有上限预警（2026-10-23 补齐 `dq.10jqka.com.cn→同花顺·热股榜`、`vip.stock.finance.sina.com.cn→新浪·行情`、`push2ex.eastmoney.com→东财·涨停池`、`smartbox.gtimg.cn→腾讯·搜索联想`，历史 9 行用 `analysis_out/api_usage_reclassify.py` 归位；接新源要同步补登记表与 `DEFAULT_LIMITS`）
  - 页面加载耗时（2026-10-30）：页头「本次加载」条由 `client-vue/src/utils/perf.js` 记录（纯内存、不落库、不发额外请求）。口径＝切页到首屏这批 `/api/*` 请求全部返回，1.2s 空闲宽限**不计入**总耗时，末帧渲染只补 <300ms；服务端耗时取响应头 `X-Process-Time`（`server/app/main.py` 中间件写入，CORS 已 expose），两者相减即隧道/传输/排队耗时。只记 `/api/*` 与 `/eastmoney/*`，`/api/auth/*` 不计
  - 页面 2s 内保障（2026-10-30）：universe/流动性 600s 缓存由调度器每 9 分钟后台保活刷新（先算好再原子换入）；批量扫描与大盘预测缓存过期后先返回旧数据、后台刷新（陈旧最长 10 分钟）；配置页口径摘要整份缓存、改配置后台重算；启动预热补批量扫描与行动台。冷算不再出现在请求路径上，重启后首开实测全部 ≤2s

  - 写事务口径（2026-11-03 实测）：`get_db_conn()` 是 `isolation_level='IMMEDIATE'` + `busy_timeout=30000`，WAL 同时只允许一个写者——**任何"先开写事务、再去等外部 IO"的代码都会把全库写锁占死**。当天踩的是回测补验：`/api/health` 抖到 8~30 秒、而同一响应 `X-Process-Time` 只有 1~2ms，说明耗时全在中间件之前排队，不在接口计算里。规矩：循环里逐条写完就 `conn.commit()` 把锁交还，外部拉数一律放在事务之外。`server/services/strategy/strategy.py` 三处已按此改（833 / 901 / 1037 行）
- 存储：通过 `trend_scan_results` 表持久化，内存缓存加速访问
- 热加载（2026-10-29 收敛后口径）：`config.py` mtime 变化时只重载 `app.config` 本身；**直接改 `config.py` 里的业务常量需重启后端生效**（写 `server/data/backend_restart_requested` 由看护重启）。常改开关走 `app_settings` 覆盖表（配置页「口径与开关」），每次取值现读，不受影响

| **每日收评**（明日关注） | 三层来源：①智能推荐(50%日内+50%趋势) → ②策略预测(`strategy_predict_records`) → ③趋势扫描高分票。**每只附「明日买入计划」**：开盘条件 + 买入价区间 + 止盈/止损 + 否决清单（盈亏比 ≥1.5） | ✅ 是 |
| **趋势发现** | `is_up_trend()` — 4 维度趋势评分（MA/资金异动/量能/回撤）+ 早期信号层 + // 乘性修正 + 动态阈值 | ❌ 独立体系 |
| **实时行情**（综合评分） | 后端 `calc_stock_score_v2` 注入 `score` 字段，前端 `utils/score.js` 透传展示（权重由后端统一维护） | ✅ 是 |

**策略权重的修改链路**：策略优化页调整权重 → `strategy_factor_weights` 表更新 → 回测自动微调 → 股票筛选/智能推荐/每日收评的评分实时变化。趋势发现和实时行情的评分完全不受策略权重影响。

详见 [评分函数对比与影响链路图](#评分函数对比) 章节。
